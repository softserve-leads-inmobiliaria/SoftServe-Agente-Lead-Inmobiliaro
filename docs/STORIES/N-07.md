# N-7 — Consultas de atribución al bot y conversión

**Épica:** E6 · Inteligencia comercial  
**Prioridad:** P1 · **Puntos:** 3 · **Track:** A  
**Depende de:** N-1, N-2

## Historia de usuario

Como gerente, quiero saber cuántos cierres trajo el bot, cuánto tarda un lead en cerrar y si el score predice bien, para medir el retorno del agente.

## Criterios de aceptación

- [ ] Módulo nuevo `services/panel/app/attribution.py`, de solo lectura, con el mismo estilo que N-6.
- [ ] Cierres atribuidos al bot según la regla de N-2, sobre el total de cierres del periodo.
- [ ] Tiempo del primer mensaje del lead al cierre: mediana y p90.
- [ ] Conversión a `closed_won` por banda del score (HOT, WARM, COLD).
- [ ] Retorno por campaña: por `utm_campaign`, leads, calificados y cierres.
- [ ] Cada consulta permite incluir o excluir los datos `synthetic`.
- [ ] Tests con datos armados en el propio test.

## Definition of Done

- [ ] Código en `main` vía PR revisado por al menos otra persona del equipo (idealmente quien consume el contrato/módulo desde el otro lado).
- [ ] Suite de tests del servicio/paquete afectado en verde en CI.
- [ ] Ningún *contract test* roto (`tests/contracts/`).
- [ ] Estado de la historia actualizado en GitHub Issues/Project — nunca en este archivo (ver `docs/ESTRUCTURA-DEL-PROYECTO.md` §5).
- [ ] Si la historia introduce o cambia una decisión de arquitectura, tiene su entrada correspondiente en `docs/DECISIONS/decisions.md`.
- [ ] El primer PR fija las firmas y los *dataclasses* de resultado, para que N-8 arme las vistas en paralelo.

## Notas de diseño

La conversión por banda sale sesgada mientras `need_fit` no cuente la propiedad del anuncio: ver A-15.
