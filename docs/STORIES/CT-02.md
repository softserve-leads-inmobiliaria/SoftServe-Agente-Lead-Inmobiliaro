# CT-2 — Congelar el contrato MCP del Catalog Service

**Épica:** E0 · Contratos y entorno  
**Prioridad:** P0 · **Puntos:** 3 · **Track:** Cross  
**Depende de:** —

## Historia de usuario

Como equipo de desarrollo, quiero el contrato de las tools `catalog.*` (input/output schema) congelado antes de implementar el catalog real, para que el orquestador y el catalog se construyan en paralelo.

## Criterios de aceptación

- [ ] Un `.schema.json` en `contracts/mcp/` por cada tool: `search_properties`, `get_property`, `get_availability`, `get_promotions`, `check_requirements`.
- [ ] Cada schema declara explícitamente sus casos de error (`NOT_FOUND`, `INVALID_INPUT`, `UPSTREAM_UNAVAILABLE`) desde el principio, no agregados reactivamente cuando aparezca el primer caso real.
- [ ] Ejemplos válidos e inválidos por tool en `contracts/examples/`.

## Definition of Done

- [ ] Código en `main` vía PR revisado por al menos otra persona del equipo (idealmente quien consume el contrato/módulo desde el otro lado).
- [ ] Suite de tests del servicio/paquete afectado en verde en CI.
- [ ] Ningún *contract test* roto (`tests/contracts/`).
- [ ] Estado de la historia actualizado en GitHub Issues/Project — nunca en este archivo (ver `docs/ESTRUCTURA-DEL-PROYECTO.md` §5).
- [ ] Si la historia introduce o cambia una decisión de arquitectura, tiene su entrada correspondiente en `docs/DECISIONS/decisions.md`.
- [ ] Un test de contrato por tool en verde.

## Notas para v2 (aprendido en v1)

Diseñar el caso de falla desde el contrato, no después, fue una de las decisiones de mayor retorno de v1 (lecciones v1 §1) — repetir.
