# N-4 — Registrar el interés del lead por cada propiedad

**Épica:** E6 · Inteligencia comercial  
**Prioridad:** P1 · **Puntos:** 2 · **Track:** A  
**Depende de:** N-1

## Historia de usuario

Como inmobiliaria, quiero saber qué propiedades vio, consultó o visitó cada lead, para poder atribuir un cierre al bot y saber qué propiedades generan interés.

## Criterios de aceptación

- [ ] `advance` (`services/core/app/turn.py`) escribe en `property_interest`, en la misma transacción del turno: `anuncio` para la propiedad del *deep-link* (`?start=prop_…`), `consulta` por cada `get_property` y `busqueda` por cada propiedad que devolvió `search_properties`.
- [ ] `visita` se escribe cuando el turno reserva una visita. Si B-8 todavía no está en `main`, esta historia deja la función lista con su test y B-8 la llama.
- [ ] La misma propiedad, con el mismo lead, tipo y turno, es una sola fila.
- [ ] Si falla el guardado, falla el turno entero, como el resto de `advance`: el historial nunca queda desfasado del estado.
- [ ] No se guarda nada del texto del lead.
- [ ] Tests en `services/core/tests` contra Postgres.

## Definition of Done

- [ ] Código en `main` vía PR revisado por al menos otra persona del equipo (idealmente quien consume el contrato/módulo desde el otro lado).
- [ ] Suite de tests del servicio/paquete afectado en verde en CI.
- [ ] Ningún *contract test* roto (`tests/contracts/`).
- [ ] Estado de la historia actualizado en GitHub Issues/Project — nunca en este archivo (ver `docs/ESTRUCTURA-DEL-PROYECTO.md` §5).
- [ ] Si la historia introduce o cambia una decisión de arquitectura, tiene su entrada correspondiente en `docs/DECISIONS/decisions.md`.

## Notas de diseño

Comparte archivos con N-5 (`turn.py`, `state_store.py`): conviene que las dos las haga la misma persona, una después de la otra.
