# A-1 — Flujo FSM coherente

**Épica:** E1 · Motor del agente  
**Prioridad:** P0 · **Puntos:** 5 · **Track:** A  
**Depende de:** CT-4

## Historia de usuario

Como lead, quiero que la conversación avance por una máquina de estados coherente (saludo → descubrimiento → recomendación → calificación → agendamiento/handoff), para tener una experiencia consistente sin importar por dónde entre.

## Criterios de aceptación

- [ ] FSM con los estados de `docs/DESIGN/design.md` §2.
- [ ] **Estado persistido en Postgres desde este commit** — no en memoria.
- [ ] Cubre todas las aristas del diseño, incluida `HUMAN_HANDOFF`.

## Definition of Done

- [ ] Código en `main` vía PR revisado por al menos otra persona del equipo (idealmente quien consume el contrato/módulo desde el otro lado).
- [ ] Suite de tests del servicio/paquete afectado en verde en CI.
- [ ] Ningún *contract test* roto (`tests/contracts/`).
- [ ] Estado de la historia actualizado en GitHub Issues/Project — nunca en este archivo (ver `docs/ESTRUCTURA-DEL-PROYECTO.md` §5).
- [ ] Si la historia introduce o cambia una decisión de arquitectura, tiene su entrada correspondiente en `docs/DECISIONS/decisions.md`.

## Notas de diseño

Postgres es la fuente de verdad del estado desde esta historia (DT-1): no existe una versión en memoria que se persista después. Así no hay que agregar la persistencia más adelante ni cuidar que memoria y base no diverjan.
